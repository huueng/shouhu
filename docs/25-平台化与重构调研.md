# 25 · 多平台与重构调研

结论先放前面：**中继值得平台化，家人端现在不值得推倒重写。**

## 一、中继（Go 单二进制）平台化难度

现状：一个静态编译的 Go 程序，全部状态在数据目录（`config.json` / `state.json` / `points.jsonl`），
网页 UI 用 `go:embed` 打进二进制。这个结构对移植非常友好 —— **没有数据库、没有外部依赖、
没有需要单独部署的前端**。

### 1.1 Docker（飞牛 / 群晖 / 任意 Linux NAS）

难度：**低**（半天以内）

需要做的：
```dockerfile
# 多阶段：构建 amd64 + arm64 + armv7 三个架构
FROM --platform=$BUILDPLATFORM golang:1.21 AS build
ARG TARGETOS TARGETARCH TARGETVARIANT
RUN CGO_ENABLED=0 GOOS=$TARGETOS GOARCH=$TARGETARCH \
    go build -trimpath -ldflags "-s -w" -o /relay .

FROM gcr.io/distroless/static
COPY --from=build /relay /relay
VOLUME /data
EXPOSE 8898
ENTRYPOINT ["/relay"]
```

需要处理的点：
- **数据目录**：镜像里用 `/data`，`ELDER_DATA=/data`
- **时区**：墙钟时间戳都用毫秒数，不受时区影响；但页面上的"几分钟前"在前端算，也没问题
- **端口**：环境变量或 `config.json` 里的 `port`
- **健康检查**：`/api/health` 直接可用（Docker HEALTHCHECK / 飞牛的健康探针）
- **权限**：`points.jsonl` 会持续写，别用只读挂载
- **CF 隧道**：官方 `cloudflared` 容器 + `--url http://relay:8898`，或飞牛自带的隧道插件

飞牛上还有一个更省事的路子：继续用 fpk，但同时发布镜像给群晖/绿联/unRAID 用。
两套产物不冲突 —— fpk 只是"包了一层 manifest + 图标"的 tar。

### 1.2 ARM（树莓派 / ARM NAS / 玩客云）

难度：**极低**（几十分钟）

Go 交叉编译一行的事：
```
GOOS=linux GOARCH=arm64 go build .     # 绝大多数 ARM NAS
GOOS=linux GOARCH=arm GOARM=7 go build .  # 32 位 ARM（树莓派 3、玩客云）
```
`CGO_ENABLED=0` 保证是纯静态，glibc / musl 都能跑。

唯一要注意的：**SD 卡写入寿命**。`points.jsonl` 每来一个点就追加一行，
一天几百行不是问题，但建议加一个"按天切分 + 保留 N 天"（目前是单文件 + KeepDays 清理），
树莓派上可以把数据目录指到 USB 盘或 tmpfs（重启丢轨迹可接受）。

### 1.3 OpenWRT（路由器上跑）

难度：**中**（2–3 天，能跑但不推荐无脑上）

能跑，但有几个硬约束：

| 约束 | 说明 | 应对 |
|---|---|---|
| 存储小 | 很多路由器 overlay 只有 16–64MB，二进制约 8MB | 编译时 `-ldflags "-s -w"`，关掉不必要的功能；用 extroot/U 盘 |
| 内存小 | 128MB 的机器跑 Go 有点紧 | Go 的 GC 在 100MB 内还行，但要压住并发（长轮询会占 goroutine） |
| 架构杂 | mips / mipsle / armv7 / aarch64 都有 | 每个架构单独出静态二进制 |
| 没有 systemd | 用 `/etc/init.d/elderrelay` + procd | 写一个 20 行的 init 脚本 |
| 写入寿命 | flash 反复写会坏 | 数据目录放 `/tmp`（重启丢轨迹）或 U 盘 |

**长轮询在路由器上反而是优势**：老人端每 25 秒挂一次，路由器只维持一个空闲 TCP，
比反复建连省。但如果几十台设备同时挂，要注意文件描述符上限（`ulimit -n`）。

建议：**先出 Docker + ARM 二进制，OpenWRT 放到"有人真的要"再做**。
真要做，优先支持 aarch64（新一代路由器、软路由都是这个）。

### 1.4 为了将来多平台，现在就该守住的三条

1. **单二进制 + 数据目录**，不要引入 SQLite/Redis（一旦引入，交叉编译立刻变复杂）
2. **接口版本化**：老人端/家人端都带 `?v=2` 或用路径 `/api/v2/...`，
   老客户端继续能用，新平台才有腾挪空间
3. **不要把平台相关的东西写进协议**：路径、编码、时区、时间格式，全部走 UTF-8 + 毫秒时间戳

## 二、家人端要不要重构？

### 2.1 现状盘点

| 项 | 现状 |
|---|---|
| 形态 | 单个 `index.html`，68KB，HTML+CSS+JS 全在里面 |
| 状态 | `localStorage`（`elder_family_v2`），一台手机一份 |
| 依赖 | Leaflet 走 CDN，其余零依赖 |
| 测试 | 无（这次是靠真机截图人肉验的） |
| 复用 | 中继 `/f` 直接托管同一份文件 |

优点：体积小、离线可用、改一行就能上线、构建成本为零。
缺点：函数之间靠全局变量串联（`db` / `curId` / `lastData`），
边界不清；本地状态没法多设备同步；没有自动化测试，改动风险全靠人肉回归。

### 2.2 结论：不推倒重写，做"分层重构"

理由：现在的痛点不是"代码烂到改不动"，而是**三个具体的功能缺口**（同步、扫码、按钮反馈），
重写一遍并不能自动解决它们，反而会把已经踩平的坑（坐标系、围栏判定、CORS、长轮询）重新踩一遍。

建议分三步，每步都能独立上线：

**第一步（已完成）**：把"谁是数据源"分清楚 —— `direct` 走老人机、`relay` 走中继，
查询/轨迹/围栏/命令四条路径都按模式分流，不再互相污染。

**第二步（1–2 天）**：抽出三个薄层，文件不变、函数搬家：
```
api.js      // fetch 封装：direct vs relay、超时、重试、错误文案
store.js    // 数据读写：现在 localStorage，将来可换成中继端存储
view.js     // 渲染：列表/详情/地图/围栏
```
UI 完全不动，只是把 `fetch(...)` 和 `localStorage` 换成调用。
这样"多设备同步"以后只需要换 `store.js` 的实现。

**第三步（按需）**：加一个 Node 冒烟测试，把这几条固定下来：
- 给定 `/api/status` 的 JSON，页面能渲染出时间/精度/电量
- 给定 `/api/track` 的点（含 `lng` 和 `lon` 两种写法），轨迹不报错
- 命令按钮在两种模式下打到正确的 URL

只有当你决定"把家人端做成产品（多用户、多设备、云端同步、消息推送）"时，
才值得换框架重写。那时候要重写的是**壳**，不是这些业务逻辑。

### 2.3 多设备/多系统兼容（现在就能定的）

- **中继托管页面**（`/f`）已经天然支持所有有浏览器的设备：手机、平板、电脑、飞牛 APP 内嵌 WebView
- 页面要照顾**手机竖屏**：`viewport` 已有，按钮最小高度 44px，表格改卡片
- iOS Safari 的两个坑：`localStorage` 在无痕模式会抛异常、`fetch` 不带 cookie —— 现在都不依赖 cookie，OK
- 微信内打开会被拦 `window.open`，所以「高德打开」失败要能复制链接（这次已经补上）
