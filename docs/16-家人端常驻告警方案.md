# 16 · 家人端常驻告警方案（放弃微信通道）

> 日期：2026-10-26
> 决策：**放弃微信/WxPusher 通道**；NAS（飞牛 fnOS + IPv6 公网）做中继；家人端 App 常驻（可开关、可选择）接收并弹系统通知。
> 状态：**中继已实现并打包（见 17），家人端 App 改造待做**。

## ⚠ 2026-10-26 决策更新（推翻本文部分设计）

用户在这一轮明确了 6 件事，其中第 1 条**推翻了原第四章的确认闭环**：

### 1. 去掉确认闭环 ← 本文第四章作废

原话：「通知上只做简单通知，不做返回确认，这个操作容易显得有人亲近，有人不亲近不管不问。」

这个判断比纯技术考量更有分量：**把"谁处理了"摊在桌面上，会让没及时处理的人难堪，最终损害的是家人之间的关系，而不是提升安全性。**

所以：
- ❌ 不做「知道了」按钮
- ❌ 不做「已由 XX 处理」的互相同步
- ❌ 不做 10 / 30 / 60 分钟升级链
- ✅ 通知就是通知，发出去即完成

**连带影响**：中继的事件表简化为**只读队列**（生成 → 排队 → 被拉走），不做 ack 状态机、不做升级调度。`event` 表不需要 `acked_by` / `state` / `escalated_at` 字段。

### 2. 双模式并存

家人端每个老人可独立选择数据来源：

| 模式 | 路径 | 适用场景 |
|---|---|---|
| **直连** | 家人机 → 老人机（现有 `LocateServer`） | 市郊、城外，信号好，轻度管控 |
| **中继** | 家人机 → NAS 中继 → 老人机 | 需要围栏告警 |

→ 家人端的老人配置要多一个 `mode` 字段，两套数据源共存，UI 上共用卡片。原直连能力**不退役**。

### 3. 多围栏，先圆后方

家一个、乡镇街一个，各自独立判定。**先实现圆形，方框/多边形后续**。

→ 中继已支持：`fence` 表 + `shape: "circle" | "polygon"`，多边形判定（射线法 + 点到边距离作为精度缓冲）已实现并通过测试。**家人端以后加画方框时，中继不用改。**

### 4. 通知图标：盾牌，初始白色

→ 已生成（`tools/gen-icon.py`，纯 Python 无 Pillow）。飞牛图标是品牌蓝底 + 白盾；Android 通知小图标需要纯白剪影，用同一轮廓即可。

### 5. ROM 覆盖范围

华为（EMUI，**非鸿蒙**）、荣耀、小米、OPPO、vivo、三星。

鸿蒙 NEXT 不再兼容 APK，是独立议题，后面单独处理。保活引导页按这 6 家做分支。

### 6. 飞牛应用走 native 版

不走 Docker（离线装会卡在拉镜像）。已完成，安装说明见 `17-飞牛中继部署手册.md`。

## 一、为什么放弃微信是对的

表面理由：iLink 24h/10 条 + 每天要家人主动发一句话保活，三五天能坚持，一年半载必然放弃。

**更硬的理由**：微信通道做不出「确认闭环」。

围栏预警的真问题不是"有没有收到"，是**"有没有人真的在处理"**。微信能做到"发出去"，做不到：

| 能力 | 微信/iLink | App 常驻 |
|---|---|---|
| 确认收到 | 回复"1"，但会消耗配额 | ✅ 点按钮，不消耗任何额度 |
| 未确认升级 | 做不到（配额还不一定够） | ✅ 10/30/60 分钟逐级升级 |
| 持续响铃直到处理 | 做不到 | ✅ 可做成来电式持续响铃 |
| 谁知道这事 | 只能靠人在群里说 | ✅ 服务端记录，互相同步"已由 XX 处理" |
| 免打扰时段 | 只能手机全局静音（会把别的也静音） | ✅ 只静音这一类 |
| 一天 20 次进出 | 额度早就爆了 | ✅ 无限制 |
| 长期可维护 | 协议/配额政策随时变 | ✅ 自己控制 |

**结论：放弃微信不是妥协，是把"能发"升级成"有人管"。**

## 三、三层送达保障

微信方案只有一条路，断了就没了。App 方案可以做三层，逐层降级：

| 层 | 机制 | 延迟 | 失效条件 |
|---|---|---|---|
| **L1** | 前台服务 + 长轮询（90 秒挂起） | < 1 秒 | 前台服务被杀 |
| **L2** | `JobScheduler` 周期任务（≥15 分钟） | ≤ 15 分钟 | 被系统彻底禁止后台 |
| **L3** | 老人端短信（已有 `SmsResponder`） | < 10 秒 | 无信号 |

L1 挂了 L2 自动补，L2 也被禁说明手机被彻底限制（用户自己清理了后台），此时 L3 的短信仍然能到。**这三层覆盖了"手机在手上但 App 没跑"这个最常见的情况。**

### 3.1 为什么用长轮询而不是 WebSocket

| 对比 | WebSocket | 长轮询（HTTP） |
|---|---|---|
| 额外依赖 | 需要 OkHttp（约 800KB） | **零依赖**，`HttpURLConnection` 就够 |
| 断线处理 | 要自己写重连/心跳/指数退避 | 下一个循环自然重连 |
| 服务端 | 要维护连接表、心跳、并发 | **无状态**，一个 `select` 挂起即可 |
| 移动网络耗电 | 需要持续心跳保活 | 一条连接挂 90 秒，请求频率更低 |
| 事件频率 | 高频才划算 | **低频事件的最优解** |

围栏预警一天几次到几十次，属于极低频。**长轮询在这个场景全面优于 WebSocket**，还省掉一个依赖。

接口形态：

```
GET /api/events?since=<cursor>&wait=90&k=<token>
→ 有事件立即返回；90 秒无事件返回 204（客户端立刻重连）
→ 返回 { cursor, events: [...] }
```

`cursor` 单调递增，客户端本地持久化，重连不会漏事件也不会重复。

## 四、确认闭环（本次最核心的设计）

### 4.1 事件状态机

```
        判定越界
            │
            ▼
        PENDING ──家人点「知道了」──→ ACKED（记录是谁、什么时候）
            │
            │ 10 分钟未确认
            ▼
      PENDING_LOUD ──仍无人──→ 30 分钟：通知其他家人
            │
            │ 60 分钟
            ▼
      PENDING_URGENT ──→ App 内提示「一键拨号」
```

### 4.2 升级规则

| 时间 | 动作 |
|---|---|
| t0 | 推通知：响铃 + 震动 + 横幅（heads-up） |
| t0 + 10 分钟 | 无人确认 → **再来一次**，响铃时间加长 |
| t0 + 30 分钟 | 无人确认 → 推给**其他家人**（避免只有一个人被通知） |
| t0 + 60 分钟 | 无人确认 → 通知里带「一键拨号」，并标记为「未处理」红色卡片 |
| 回到围栏内 | 自动 ACK 一条「已回到围栏内」，关闭所有未确认事件 |

### 4.3 互相同步

任一家人确认后，其他人**下次拉取时**收到「已由 姐姐 处理」并自动消除自己那条通知。避免全家被反复打扰。

> 这是微信方案完全做不到的——微信里只能靠人在群里打字。

## 五、中继服务设计

### 5.1 接口

| 方法 | 路径 | 用途 | 鉴权 |
|---|---|---|---|
| POST | `/api/report` | 老人端上报 | device token |
| GET | `/api/events?since=&wait=` | 家人端长轮询 | family token |
| POST | `/api/ack` | 确认事件 | family token |
| GET | `/api/status` | 最新快照（家人端 App 复用） | family token |
| GET | `/api/track?since=` | 轨迹 | family token |
| GET | `/api/fence` | 读围栏 | family token |
| POST | `/api/fence` | 增/改/删围栏 | family token |
| GET | `/api/config` / POST | 提醒偏好（安静时段等） | family token |
| GET | `/api/health` | 健康检查 | 无 |

### 5.2 表结构

```sql
device ( id TEXT PK, name TEXT, token TEXT, last_seen INTEGER, last_json TEXT )

position ( device_id TEXT, t INTEGER, lat REAL, lon REAL, acc INT, src TEXT )
-- 全量存，按 (device_id, t) 建索引；超过 90 天自动删

fence ( id TEXT PK, device_id TEXT, name TEXT, lat REAL, lon REAL,
        radius INT, enabled INT, created_at INTEGER )

fence_state ( device_id TEXT, fence_id TEXT, inside INT,
              since INTEGER, last_acc INT, pending_cnt INT,
              PRIMARY KEY (device_id, fence_id) )

event ( id TEXT PK, device_id TEXT, fence_id TEXT, kind TEXT,
        t INTEGER, lat REAL, lon REAL, dist REAL, acc INT,
        state TEXT,          -- PENDING / PENDING_LOUD / PENDING_URGENT / ACKED / AUTO_CLOSED
        acked_by TEXT, acked_at INTEGER, escalated_at INTEGER )

pref ( device_id TEXT, quiet_start INT, quiet_end INT,
       ring_mode INT,      -- 0 通知 / 1 响铃 / 2 持续响铃
       enabled INT )
```

### 5.3 围栏判定（关键，防误报）

```
d   = 与围栏中心距离（haversine）
r   = 半径
acc = 该点定位精度

acc > r * 1.5     → 精度太差，本轮不判定，维持上一状态
d - acc > r       → 确定在外
d + acc < r       → 确定在内
其余               → 不确定带，维持上一状态
```

叠加三条：

| 规则 | 作用 |
|---|---|
| 连续 2 点确认 | 单点漂移不报 |
| 同状态 30 分钟内去重 | 边界抖动不刷屏 |
| 回围栏也推 | 家人要知道人回来了 |

**为什么必须这样**：老人机室内多为网络定位，精度 300–1000 米，而围栏半径典型 300–500 米。不做迟滞必然疯狂误报，误报三次这个功能就被家人关掉了。

### 5.4 技术选型

| 项 | 选择 | 理由 |
|---|---|---|
| 语言 | **Go**，静态编译单二进制 | 镜像 < 20MB、内存 < 30MB、无运行时依赖 |
| 存储 | **SQLite**（CGO 版，x86/ARM 上没障碍） | 表结构清晰，家人端要按时间查 |
| 部署 | Docker，`network_mode: host` | 见第六节，host 模式是 IPv6 的关键 |

## 六、飞牛（fnOS）Docker 的 IPv6 坑（必须注意）

**Docker 默认的 bridge 网络不支持 IPv6。** 这是本次部署最容易卡住的地方。

三种解法，按推荐排序：

| 方案 | 做法 | 评价 |
|---|---|---|
| **host 网络** | `docker-compose.yml` 里 `network_mode: host` | ✅ **最省事**，容器直接用宿主 IPv6，不折腾 |
| 开启 Docker IPv6 | `/etc/docker/daemon.json` 加 `"ipv6": true, "fixed-cidr-v6": "fd00::/80"` + 容器 `--ipv6` | 需要 NAT66 或路由，麻烦 |
| 反向代理 | 飞牛自带的网关/反代监听 IPv6，转发到容器 | 多一层，但证书好配 |

**推荐 host 模式**，同时解决两件事：IPv6 直通、端口不用映射。

其他飞牛侧要点：

1. **容器端口**：不要用 8899（老人机 `LocateServer` 已占用），中继用 **8898** 之类
2. **防火墙**：飞牛若开了防火墙，要放行 inbound TCP 8898（v6）
3. **DDNS**：中继的可达地址是 `xxx.dynv6.net:8898`，靠现有 `DdnsUpdater` 更新 AAAA
4. **休眠**：确认 NAS 不会因硬盘休眠挂起容器（Docker 容器本身不受硬盘休眠影响，但要注意日志盘）
5. **自启**：`restart: unless-stopped`，NAS 重启后中继自动起来

## 七、家人端 App 设计

### 7.1 现状与需新增

现状（读代码确认）：`targetSdk 29`，权限只有 `INTERNET` + `ACCESS_NETWORK_STATE`，依赖只有 appcompat + zxing，纯 WebView 壳。

需要新增：

| 项 | 内容 | 新依赖 |
|---|---|---|
| 前台服务 | `AlertService`，常驻通知，跑长轮询循环 | 无 |
| 系统通知 | `NotificationChannel` 高优先级（响铃+震动+横幅） | 无 |
| 通知按钮 | 「知道了」直接 ACK，不进 App | 无 |
| 开机自启 | `BOOT_COMPLETED` 拉起前台服务 | 无 |
| 兜底轮询 | `JobScheduler`，`setPeriodic(15min)` | 无 |
| 网络状态 | 复用现有 `ACCESS_NETWORK_STATE` | 无 |
| 保活引导 | 自检页，逐项跳系统设置 | 无 |

**好消息：全部零新依赖。** 不用 OkHttp、不用 WorkManager、不用 Firebase。

### 7.2 targetSdk 29 带来的便利与限制

| 项 | 情况 |
|---|---|
| 前台服务类型 | 29 不强制 `foregroundServiceType`，省掉一堆声明 |
| 通知权限 | Android 13+ 需要 `POST_NOTIFICATIONS`，但 targetSdk<33 时系统按兼容处理；**保险做法还是加声明 + 首次启动弹一次** |
| 精确闹钟 | 不用（改用 `JobScheduler`，不需要 `SCHEDULE_EXACT_ALARM`） |
| 后台启动 Activity | Android 10 起受限 → **通知点击启动 Activity 不受限**（用户点击是允许的） |

### 7.3 保活清单（国产 ROM 逐项）

这是家人端能不能"常驻"的决定性环节，必须在 App 里做成一个「一键自检」页（参考老人端的 `GuardianCheckActivity`）：

| # | 措施 | 用户操作 | 华为/荣耀 | 小米 | OPPO/vivo |
|---|---|---|---|---|---|
| 1 | 前台服务常驻通知 | 无 | ✅ | ✅ | ✅ |
| 2 | 电池优化白名单 | 一键弹窗 `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` | 应用启动管理 → 手动管理 | 省电策略 → 无限制 | 耗电管理 → 允许后台 |
| 3 | 自启动 | 跳系统设置 | 应用启动管理 | 自启动 | 自启动 |
| 4 | 后台弹窗（横幅） | 跳系统设置 | 允许 | 显示悬浮窗 | 允许 |
| 5 | 最近任务锁定 | 图文引导 | 下拉加锁 | 长按加锁 | 下拉加锁 |
| 6 | 通知权限 | 一次性弹窗 | ✅ | ✅ | ✅ |
| 7 | 锁定后台清理白名单 | 跳设置 | ✅ | ✅ | ✅ |

**做 1–2 项就能活到 90% 的场景；3–5 项补齐才能扛住"一键清理"。**

### 7.4 通知设计

```
┌────────────────────────────────┐
│ 守护 · 爷爷离开了安全范围        │
│ 10:23 · 距围栏中心 780 米       │
│ [知道了]  [看地图]              │
└────────────────────────────────┘
```

- `IMPORTANCE_HIGH` → 横幅 + 声音 + 震动
- 通知 ID 按事件 ID 分配，不覆盖（多次越界各自一条）
- 点击「知道了」→ 直接 ACK（`PendingIntent` 到 BroadcastReceiver，不打开 App）
- 点击「看地图」→ 打开 App 并定位到该老人
- 安静时段：只降级为无声通知 + 图标角标，**不丢弃**

### 7.5 「可开关、可选择」的具体含义

| 开关 | 粒度 |
|---|---|
| 总开关 | 关闭后不常驻、不通知（App 只做手动查询） |
| 每个老人独立开关 | 多老人时可只订阅其中一位 |
| 每个围栏独立开关 | 家 / 子女家 / 公园 可以只关心其中一个 |
| 提醒方式 | 通知 / 响铃 / 持续响铃（来电式） |
| 安静时段 | 例如 22:00–07:00 只发无声通知 |

全部存 NAS 的 `pref` / `fence` 表，多家人共享同一份配置，不用每人各设一遍。

## 八、老人端改动

改动很小，但都是必需的：

| # | 改动 | 现状 |
|---|---|---|
| 1 | 上报间隔可配（默认 10 分钟） | 固定 60 分钟（`ReportUploader.INTERVAL_MS`） |
| 2 | **每次采样都上报当前位置**，不只在"移动 ≥80m"时记点 | `TrackReceiver` 只在移动/静默时才落点 |
| 3 | 上报带 `acc`（精度）和 `event` 字段 | 已有 `acc`，缺 `event` |
| 4 | 支持 2 个上报地址，主失败切备 | 单地址 |
| 5 | 断网时本地排队，恢复后补报 | 当前直接丢弃 |
| 6 | 低电 / 锁任务被关 / 定位被关 时立即上报一次 | 无 |

**不用改的**：`LocateServer`（家人端手动查询仍走它）、`DdnsUpdater`、`SmsResponder`。

## 九、端到端时延

| 环节 | 耗时 |
|---|---|
| 老人走出围栏 | 0 |
| 等下一次采样 | 0–10 分钟（`setInexactRepeating` 可能再延后到 15 分钟） |
| 上报到 NAS | 1–3 秒 |
| 中继判定 + 入队 | < 100 ms |
| 长轮询立即返回 | < 1 秒 |
| 通知弹出 | < 1 秒 |
| **合计** | **典型 5 分钟，最差 15 分钟** |

走失处置的黄金窗口是 1 小时，5 分钟完全够。

**要更快**（第二期）：围栏配置下发到老人端，老人端本地判定，越界立刻单发一条上报并临时把采样提到 1 分钟。

## 十、网络可达性风险（必须正视）

中继只有 IPv6，意味着**家人端必须拿到 IPv6 才能连**。

| 家人所在网络 | 能否连上 |
|---|---|
| 家里 WiFi（有 IPv6） | ✅ |
| 手机移动数据（三大运营商） | ✅ 基本都有 |
| 公司 WiFi / 商场 WiFi（IPv4-only） | ❌ **连不上** |
| 酒店 / 高铁 | ❌ 大概率 |

这是 IPv6-only 方案的先天缺陷。三种应对：

| 方案 | 成本 | 效果 |
|---|---|---|
| **A. 接受**，App 里明确提示「当前网络不支持 IPv6，暂时无法接收」 | 0 | 最诚实，但关键时刻可能收不到 |
| **B. 加一台 VPS 做 IPv4 入口**（中继数据同步过来） | 100–300/年 | 彻底解决 |
| **C. Cloudflare Tunnel 暴露一个 HTTPS 入口** | 0 + 域名 | 国内线路不稳，可能超时 |

**建议：先做 A（明确提示），观察一个月实际有多少次连不上。** 如果家人经常在 IPv4-only 网络下且确实错过告警，再加 B。

**注意**：不要静默失败。App 后台连不上时，前台服务的常驻通知要显示「未连接」，让家人自己知道现在收不到。

## 十一、安全

中继的 8898 端口暴露在公网 IPv6 上，会被扫到。

| 项 | 措施 |
|---|---|
| 传输 | 首版可 HTTP（内网/自用），**建议尽快上 TLS**（飞牛反代 + Let's Encrypt，或自签 + App 内固定证书） |
| 鉴权 | 老人端与家人端**用不同 token**，都存在 NAS |
| 限流 | 同一 IP 失败 10 次 / 5 分钟 → 封 10 分钟 |
| 端口 | 用非标准端口（8898），减少扫描命中 |
| 数据 | 位置是敏感数据，`position` 表按 90 天自动清理 |
| 越权 | 家人端 token 只能读自己绑定的 device，不能跨设备 |

## 十二、分期

### P0 · 中继最小可用（先把链路打通）

- Go 服务 + SQLite，Docker 部署在飞牛
- `POST /api/report` 收上报（老人端临时用 ADB 或改一行配置指过来）
- `GET /api/health` 用手机浏览器验证 IPv6 可达
- **验证点：老人端能不能稳定把点送到 NAS**

### P1 · 围栏判定 + 事件队列

- 围栏表 + 迟滞判定 + 连续 2 点确认 + 去重
- `GET /api/events?wait=90` 长轮询
- 用 `curl` 模拟家人端验证
- **验证点：模拟 20 个点，误报几次**

### P2 · 家人端常驻

- 前台服务 + 长轮询循环 + 系统通知
- 通知按钮 ACK
- 保活自检页
- **验证点：锁屏放一夜，第二天还在不在线**

### P3 · 闭环与升级

- 升级调度（10/30/60 分钟）
- 多家人互相同步
- 安静时段、按围栏开关

### P4 · 老人端优化

- 上报频率可配、每次采样都上报、多地址 fallback、断网补报

## 十四、一句话总结

**放弃微信之后，方案反而更简单：不依赖任何第三方、不需要保活、不消耗额度，还能做出微信做不到的「确认 + 升级」。**

**真正的难点只剩三个**：飞牛 Docker 的 IPv6（用 host 网络解决）、老人机定位精度（用迟滞带解决）、家人端国产 ROM 保活（用自检引导 + 三层兜底解决）。
