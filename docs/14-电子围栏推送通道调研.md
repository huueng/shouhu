# 14 · 电子围栏主动推送通道调研

> 调研日期：2026-10-26
> 范围：**只做「老人离开/回到围栏」的主动推送**。微信里不做指令查询，主动查位置仍走家人端 App。
> 前置：DDNS 能力保留（不退役），作为可选路径。

---

## 一、需求重新定义

现有围栏的真实状态（读代码确认）：

| 项 | 现状 |
|---|---|
| 围栏配置 | 存在**家人端 App 的 localStorage**（`e.fence = {lat, lng, radius}`） |
| 判定位置 | **家人端 JS**（`checkFence()`，`index.html:641`） |
| 触发时机 | 只有点「自动查」并轮询时才判定，**App 关闭 = 完全不判定** |
| 位置来源 | 家人端实时拉老人机 `/loc`（按需定位） |

**所以现在的围栏不是围栏，是"你盯着看的时候顺便算一下距离"。**

要变成真围栏，三件事必须改：

1. 围栏配置从家人端 localStorage → **搬到中继**（否则中继不知道围栏在哪）
2. 判定从家人端 JS → **搬到中继**（否则家人不开 App 就没有判定）
3. 位置从"被查询才取" → **老人端定时上报到中继**

第 3 项正好是 `docs/11` 里列为 ★★★★★ 的「老人端主动上报」，本次一并解决。

## 二、通道选型：iLink（微信 ClawBot）

### 2.1 它是什么

2026 年 3 月腾讯通过 OpenClaw 生态开放的**官方个人微信 Bot 接口**，底层协议 `iLink`：

| 项 | 值 |
|---|---|
| 接入域名 | `https://ilinkai.weixin.qq.com` |
| 协议 | 纯 HTTP/JSON（**不是** WebSocket、**不是**协议破解） |
| 鉴权 | 扫码登录拿 `bot_token`，请求带 `Authorization: Bearer {token}` + 随机 `X-WECHAT-UIN` |
| 核心端点 | `/ilink/bot/get_bot_qrcode`、`/get_qrcode_status`、`/getupdates`（35s 长轮询）、`/sendmessage`、`/sendtyping`、`/getconfig` |
| 消息类型 | 文字、图片、语音（SILK）、文件 |
| 法律依据 | 《微信ClawBot功能使用条款》 |
| 费用 | 免费（无 API 计费） |

### 2.2 硬限制（决定方案能不能用）

| # | 限制 | 对围栏场景的影响 |
|---|---|---|
| 1 | **用户发消息后 24h 内，bot 最多主动发 10 条**（含回复那条） | ⚠️ 最大约束。一天进出围栏超过 10 次就推不出去 |
| 2 | **必须由用户先发过消息**，bot 才有推送窗口 | ⚠️ 家人加入后要先发一句「在」，之后每 24h 至少要再说一句才续窗口 |
| 3 | 仅支持私聊，**不支持群聊** | 不能拉「家庭群」，每人单独加 bot 好友 |
| 4 | 一个 bot = 一个真实微信号 | 需要一个闲置微信号来当 bot，这个号会被占用 |
| 5 | 微信客户端 ≥ 8.0.70 | 家人微信版本不能太旧 |
| 6 | Markdown 渲染不稳，表格/代码块会乱码 | 推送内容只能用纯文本 + emoji 分隔 |
| 7 | `bot_id` 与微信号 1:1 写死，不可解绑恢复 | 换号要重扫，老的作废 |
| 8 | token 24h 有效期（插件自动续，自研要自己续） | 自研要注意续期逻辑 |

### 2.3 关键结论：WxPusher 的微信渠道就是 iLink

WxPusher 官方文档已明确其「微信 ClawBot（iLink）推送渠道」的限制与上面完全一致（**24 小时内最多 10 条**）。

所以 **WxPusher 并不能绕开 10 条限制**，它只是帮你省掉「养一个小号」和「自己实现协议」。

| 路径 | 是否需要自己的号 | 推送额度 | 家人要做什么 |
|---|---|---|---|
| iLink 直连 | 要（闲置微信号） | 24h / 10 条 | 加 bot 为好友 |
| WxPusher + 微信渠道 | 不要 | 24h / 10 条 | 关注 WxPusher 公众号 |
| **WxPusher + App** | 不要 | **单日 3000 条** | 装 WxPusher App |
| 自建公众号（被动回复） | 不要 | 不能主动推 | 关注公众号 |

### 2.4 选型建议

```
家人愿意装一个 App？
├─ 愿意 → WxPusher App 通道
│          额度 3000 条/天，最可靠，不受 10 条限制
│          代价：又一个 App，且要在 App 里开通知权限
└─ 只用微信 → 24h / 10 条
        ├─ 有闲置微信号 → iLink 直连（好友形态，最原生，能收能回）
        └─ 没有         → WxPusher 公众号（省事，但只能看不能回）
```

**推荐组合：WxPusher App（主）+ iLink 小号（备）**。两条通道并联，任一条通就能收到。围栏预警这种低频高价值事件，值得做双通道。

### 2.5 24h/10 条怎么应对

围栏预警是低频事件，一天真进出不了 10 次，所以额度本身够用。真正的风险是**窗口过期**（家人 24h 没跟 bot 说话）。

三个对策，按优先级：

1. **每日汇总保活**：每天 20:00 推一条「今日小结」（消耗 1 条）。家人看到随手回个「1」，窗口就续上了。
2. **预警带确认**：预警消息末尾写「回复 1 表示知道了」。回复既是确认，也重置配额。
3. **短信兜底**：极端情况（窗口过期 + 手机不在身边）走已有 `SmsCommandReceiver` / `SmsResponder`，短信不依赖数据网。

> **必须承认的结论**：微信通道**做不到 100% 可靠送达**。围栏预警是安全类事件，不能只挂一条通道。这不是缺陷，是 iLink 的设计（防滥用）。

## 三、围栏判定设计（比通道更关键）

### 3.1 精度问题——最大的坑

老人机在室内基本拿不到 GPS，走基站/WiFi 定位，**精度常在 300–1000 米**。而典型围栏半径是 300–500 米。

**精度 800 米的点去判 500 米围栏 = 必然疯狂误报。** 家人第一天被误报三次，第三天就会关掉这个功能。

现有代码已经埋了伏笔：`LocationHelper` 有「精度 > 120m 加提示」，`TrackStore` 存了点位精度。判定必须用上：

```
d   = 与围栏中心距离（haversine）
r   = 围栏半径
acc = 该点的定位精度

acc > r * 1.5          → 精度太差，本轮不判定，维持上一状态
d - acc > r            → 确定在外（整个误差圆都在围栏外）
d + acc < r            → 确定在内
其余                    → 不确定带，维持上一状态
```

这条「迟滞带」规则能把误报压到接近 0，代价是边界附近的判定变钝。对老人安全来说，**宁可少报也不误报**。

### 3.2 防误报的另外三条

| 规则 | 说明 |
|---|---|
| 连续 2 点确认 | 单点在外不报，连续两个采样点都在外才报（漂移通常只影响单点） |
| 状态去重 | 同一状态 30 分钟内不重复推 |
| 回围栏也推 | 「已回到围栏内」比只报离开更重要——否则家人不知道人回来没有 |

### 3.3 围栏中心怎么定

现在的做法是「取当前位置 + 输入半径」。问题：如果家人是在老人已经出门时设的，中心就设错了。

三个改法（按实现成本排序）：

1. **提示 + 校验**：设置时若 `accuracy > 200`，提示「定位不准，建议老人在家时再设」
2. **取停留点**：用最近 3 天轨迹里停留时间最长的聚类中心作为默认中心
3. **多点围栏**：家 + 子女家 + 常去的公园，各自一个圆（数据结构上 `fence` 从对象改成数组）

第一版做 1 就够。数据结构建议**一开始就用数组**，避免以后改表。

### 3.4 端到端时延

| 环节 | 耗时 |
|---|---|
| 老人走出围栏边界 | 0 |
| 等下一次采样（`TrackReceiver` 10 分钟一次，`setInexactRepeating` 可能再延后） | 0–15 分钟 |
| 上报到中继 | 1–3 秒（有网） |
| 中继判定 + 调用推送 | < 2 秒 |
| 微信/App 送达 | 1–5 秒 |
| **合计** | **典型 5 分钟，最差 15 分钟** |

**够用吗？** 走失的黄金处置窗口是 1 小时，5 分钟延迟完全可接受。

**要更快怎么办？** 两个办法，都不必第一版做：
- 中继发现越界后，回一条指令给老人端「接下来 10 分钟每分钟采样」（需要老人端有拉取通道，或走短信）
- 围栏配置下发给老人端，老人端本地判定，越界立刻单发一条上报

## 四、推送内容设计

纯文本，emoji 分隔（iLink 对 markdown 不稳）：

```
⚠ 爷爷离开了安全范围

时间  10:23
位置  北京市海淀区中关村大街 27 号
距离  离开围栏中心约 780 米（半径 500 米）
地图  https://<你的域名>/m/abc123

回复 1 表示知道了
```

要点：

- **第一行就说结论**，家人不用读细节；
- 带**距离数字**，比"已越界"有用得多；
- 带地图链接（H5，服务器渲染，不需要装 App）；
- 带"回复 1"，既做确认也续配额；
- `summary` 控制在 20 字内（WxPusher/微信通知栏会截断）。

## 五、和现有代码的映射

| 现有 | 改动 |
|---|---|
| `family/assets/index.html` `checkFence()` | 保留作"本地快速预览"，真正的判定移到中继；围栏配置改为 `POST /api/fence` |
| `TrackReceiver`（10 分钟采样，移动 ≥80m 或静默 >30min 才记点） | **不能直接用**。围栏判定需要"每次都上报当前位置"，而不是"动了才记点"。需加独立的上报节拍，或把每次采样都上报（不记轨迹也上报） |
| `ReportUploader`（每小时 POST 完整 JSON） | 频率改可配（默认 10 分钟）；围栏判定所需的字段是 `track` 最后一点或单独的 `lastPos` |
| `LocateServer`（老人机当服务器） | 保留。家人端 App 主动查询仍走它，与中继并行 |
| `DdnsUpdater` | 保留（用户要求），中继若部署在 NAS 也需要它解析 AAAA |
| `SmsCommandReceiver` | 保留作兜底通道 |

**老人端最小改动清单**：
1. 上报间隔可配（默认 10 分钟）
2. 每次采样都上报「当前点」，不只在"动了"时记轨迹
3. 上报里加一个 `event` 字段（`tick` / `boot` / `lowbat` / `call`），便于中继区分
4. （可选）支持从上报响应里读回「是否越界」，用于本地加速采样

## 七、一句话结论

**能做，而且现在有官方通道了。但真正的工作量不在接微信，在于：围栏配置要搬家、位置要变成主动上报、精度不足要设计迟滞规则。微信只占 10% 的活。**
