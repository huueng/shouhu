# 版本兼容策略

> 一句话：**新的中继 + 旧的家人端 + 更旧的老人端，必须能一起工作。**
> 家人端不一定有条件常更新（老人机可能装完就再没碰过），一次装好就该一直能用。

## 为什么这条最重要

三端的更新成本差得很远：

| 部件 | 谁来更新 | 更新成本 |
|---|---|---|
| 中继 | 家人（一条 docker pull / 重装 ipk） | 低 |
| 家人端 | 家人自己 | 中 |
| 老人端 | 得拿到老人的手机 | **高，常常几个月不动** |

所以"向下兼容"不是礼貌，是硬约束：**任意一次更新都不能让最旧的那台设备变砖。**

## 中继侧的规则

### 只加不改

- 新增字段：老端不认识就忽略 → 允许
- 新增接口：老端不调用 → 允许
- 改字段含义、改单位、改默认值语义 → **禁止**（除非走大版本）
- 删字段：至少要保留两个大版本；期间只标记 `deprecated`
- 改已有接口的**错误码/成功语义** → 视为破坏性变更

### 现状（1.15.0）

以下是已经下发到老人端的字段，属于"冻结"区：

| 接口 | 冻结内容 |
|---|---|
| `POST /api/report` | `t/lat/lon/lng/acc/battery/charging/online/version/...` 含义与单位 |
| `POST /api/report` 响应 | `ok` 必返；`cmd` 可以是新命令名（老端不认识就跳过，不算错） |
| `GET /api/wait` | 长轮询语义、`t` 超时参数（秒） |
| `GET /api/status` | 已透出的字段不删、不改单位 |
| 二维码内容 | `elderguard://relay?base=<url>&k=<token>&n=<name>` 参数只加不删 |

> 老人端对不认识命令名的处理必须是**忽略并继续跑**，不能报错退出。
> 这条在 `RemoteCommand.exec` 里已经保证：未知命令返回 `ok=false, msg=未知命令`，不影响下一轮。

### 老人端方向

老人端可能永远停在某个旧版本，所以中继要能容忍：

- 缺字段（例如老版本只发 `lng` 不发 `lon`）→ 归一化处理，别当 0
- 少接口（老版本没有 `/api/wait`）→ 退化成"等下一轮上报"，不报错
- 多发字段 → 忽略

## 家人端侧的规则

家人端是 WebView + 一份 HTML，更新相对容易，但同样按"只加不改"来：

- 页面请求的接口，中继要保证一直在；
- 中继返回的多余字段，页面要能忽略（不要 `JSON.parse` 后严格校验字段集合）。

## 版本号怎么走

`主版本.次版本.修订`

- 修订号：修 bug，无协议变化
- 次版本号：加功能、加字段（**兼容**）
- 主版本号：允许破坏性变更，且必须在 Release 说明里写清"谁必须一起升"

当前中继 1.x 期间承诺：**不出现主版本升级**。真的需要破坏性改动时，
会同时提供兼容层（同一进程内同时支持新旧两套字段），而不是让老端硬升。

## 升级顺序

任意顺序都可以：

- 先升中继 → 旧老人端/家人端照常工作
- 后升家人端 → 新功能才出现
- 老人端可以不升

**唯一要求**：升中继前备份 `/etc/elderrelay`（或 Docker 的 `relay-data`），
里面有设备令牌 —— 丢了就得去老人手机上重新扫码。

## 检查清单（发版前）

- [ ] 新中继 + 上一版老人端：上报、命令、定位正常
- [ ] 新中继 + 上一版家人端：列表、轨迹、围栏、命令正常
- [ ] 旧中继 + 新家人端：不崩溃（新字段老中继没有，页面要能兜住）
- [ ] 二维码内容与旧版一致（老老人端还能扫）
