# 13 · 微信推送 / 指令查询方案评估

> 评估日期：2026-10-26
> 触发问题：「能不能做个服务，接收老人端上报，绑定微信机器人主动推给家人，家人发简单指令就能查数据？」

---

## ⚠ 2026-10-26 结论修订（重要）

本文写作当天发现一项关键变化，**原「个人微信机器人一律否决」的结论已失效**：

**腾讯于 2026 年 3 月正式开放 iLink Bot API（微信 ClawBot）**，接入域名 `ilinkai.weixin.qq.com`，纯 HTTP/JSON，扫码登录即用，有《微信ClawBot功能使用条款》作为法律依据，**不再需要任何逆向/Hook/协议破解**。

因此「个人微信机器人」从**红区（封号）**变为**黄区（官方但受限）**，核心限制是：

> 用户向 bot 发消息后 24 小时内，bot 最多主动发 10 条（含回复那条）。配额用尽或窗口过期，需用户再发一条消息重置。

**范围也随之收窄（用户 2026-10-26 决定）**：
- 本轮只做 **电子围栏主动推送**；
- 主动查询继续走家人端 App，**不做微信指令**；
- **DDNS 能力保留**，不退役，作为可选路径。

→ 围栏推送的专项调研见 `14-电子围栏推送通道调研.md`，中继部署三档分析见 `15-中继部署三档分析.md`。
→ 本文以下章节作为**全量通道评估底稿**保留，其中「指令/推送互斥」等分析仍有效，但「个人微信机器人否决」一条请以上述修订为准。

## 一、结论（原版，仅适用于自建公众号路线）

**能做，但「微信机器人」这个词要拆开看。**

- 「个人微信机器人」——**否决**。官方从未开放普通微信群/个人号机器人接口，所有方案都是协议破解，封号风险不可接受。
- 「微信官方通道」——**可行**，但要接受一个事实：**没有任何单一官方通道能同时做到「免费 + 纯微信 + 既能主动推、又能收指令」**，必须组合两条通道。
- 真正的架构收益不在微信，而在**引入中继**：老人端从"当服务器"改成"往外上报"，可以把 IPv6、DDNS、端口映射、家人端直连这一整套脆弱依赖全部退役。

**推荐起步方案：中继服务跑在 OpenWrt/NAS（0 元）+ WxPusher 做主动推送（0 元）+ 自建订阅号做指令查询（0 元）。**

## 二、微信通道能力矩阵（已核实）

| 通道 | 主动推送 | 收指令 | 家人侧成本 | 钱 | 硬限制 |
|---|---|---|---|---|---|
| **WxPusher** | ✅ | ❌ | 关注一个公众号 | 0 | 单 UID 约 2000 条/日；`summary` 超 20 字在微信里截断；QPS ≤ 2 |
| **自建订阅号**（个人可注册） | ❌ | ✅ 被动回复 | 关注你的公众号 | 0 | 必须 5 秒内返回；服务器配置**只认 80/443，不能带端口** |
| **认证服务号** | ✅ 模板消息 | ✅ 客服消息 | 关注 | 300/年 + 企业主体 | 模板消息需选类目、过审核；个人主体不能注册服务号 |
| **企业微信自建应用** | ✅ 无限制 | ✅ | 装企业微信（可开「微信插件」在微信里收） | 0 | 家人需加入你的组织；未认证企业成员上限 200 |
| **企业微信群机器人** | ✅ 20 条/分 | ❌ | 装企业微信 | 0 | **只能内部群，外部群/含微信用户的群不支持** |
| **微信客服**（kf.weixin.qq.com） | ❌ | ✅ | 微信内点链接即聊 | 0 | 用户发消息后 48h 内最多回 5 条；**没互动过就发不出去** |
| ~~个人微信机器人~~ | ✅ | ✅ | 无 | $50/月 | **违反账号规范，封号风险，否决** |

### 为什么「主动推」和「收指令」天然互斥

- 主动推 = 模板消息 / 订阅通知 / 应用消息 → 必须事先有资质或授权；
- 收指令 = 被动回复 / 客服消息 → 只在用户发消息后的窗口内才免额度。

WxPusher 走的是它自己的服务号模板消息，所以能推不能收；你自己公众号的被动回复不占额度，但只有用户发消息才能回。**两者不是同一个账号，所以指令和推送必须在两个入口。**

## 三、被否决的方案

### 3.1 个人微信协议机器人（GeWe / Wechaty+padlocal / WeChatFerry / itchat）

| 项 | 实测情况 |
|---|---|
| 官方支持 | 无。微信至今没有开放普通微信群机器人 API |
| 成本 | padlocal token 约 $50/月；GeWe 按量；自建 hook 免费但要维护逆向 |
| 稳定性 | Web 协议已大面积封禁；iPad 协议需与账号同省 IP，消息 ≤5 条/分 |
| **本场景风险** | **封号 = 全家失联**。守护类产品的容灾要求是「不能因为通道作妖而失联」，这条红线过不去 |

**结论：不做。** 即使它体验最好（能进家庭群、能 @ 人、能主动发），也不值得拿主号去赌。

### 3.2 企业微信群机器人绑定家庭群

技术上最省事（一个 webhook URL，POST JSON 即可，免费无限），但**官方明确只支持内部群，外部群（含微信用户）不支持配置群机器人**（腾讯云告警文档也写明此限制）。家人必须全部是企业微信成员，且群必须是企业内部群。

→ 如果家人愿意装企业微信，走「自建应用」而不是「群机器人」，功能更全（应用消息不限 48h）。

## 四、架构改造（这是本次最有价值的部分）

### 4.1 现状的脆弱点

```
老人机（当服务器 8899 端口） ←──直连── 家人端 App
        ↑
   IPv6 + DDNS + 路由器端口映射 + 运营商不封入向
```

| 脆弱点 | 表现 |
|---|---|
| 依赖 IPv6 | 家里宽带没下发 IPv6 / 老人出门切移动数据 → 完全不可达 |
| 依赖 DDNS 正确 | dynv6 记录错了、token 过期 → 家人端连不上，且**没有任何提示** |
| 依赖老人机不休眠 | 息屏深度休眠后 socket 可能被回收，服务假死 |
| 数据只在本机 | 轨迹最多 500 点，重装/换机/清数据即丢 |
| 换网络即断 | 老人去子女家/住院，WiFi 一换 IP 全变 |

### 4.2 中继后的架构

```
老人端 ──HTTP POST 上报──→ 中继服务（OpenWrt / NAS / 小 VPS）
                              ├─ SQLite 落库（完整历史）
                              ├─ 规则判定 → WxPusher 推送 → 家人微信 N 人
                              ├─ /wx 回调 → 公众号被动回复（5 秒内）
                              ├─ /m/<token> → H5 地图页（微信内点开）
                              └─ /api/* → 家人端 App（可选保留）
```

### 4.3 收益对照

| 项 | 现状 | 中继后 |
|---|---|---|
| 老人端网络要求 | 必须有公网 IPv6 入向 | **只要能用 WiFi 上网**（NAT 后面也行） |
| DDNS | 必需 | **可退役** |
| 路由器端口映射 | 必需 | **可退役** |
| 家人端必须装 App | 是 | 否（微信即可看，App 降级为深度查看） |
| 轨迹历史 | 500 点上限 | 取决于存储，可存数月 |
| 失联感知 | 无（家人端打不开也不会告警） | **有（超过 N 分钟没上报就推一条）** |
| 多人共享 | 每人都要装 App + 手填地址密钥 | 关注同一个公众号即可 |

### 4.4 复用的现成能力（改动量极小）

`ReportUploader` 已经在做「每小时 POST 一份完整 JSON 到可配置 URL」，payload 结构正好就是中继需要的：

```json
{
  "device": "Xiaomi Redmi 9A",
  "version": "2.0",
  "time": 1761450000000,
  "status": { "battery": 76, "charging": false, "ringVolume": 0, "muted": true,
              "storageFreeMB": 2048, "lockTask": true, "locateOn": true,
              "wifi": true, "wifiName": "home", "topApps": [...] },
  "diag": {...},
  "usage": [...],
  "track": [ { "t": ..., "lat": ..., "lon": ..., "acc": ... } ],
  "trackSince": 1761440000000,
  "trackLastT": 1761450000000
}
```

**老人端第一版可以一行代码都不改**，只需要在设置里把「上报地址」填成中继的 `/api/report`。

### 4.5 但上报频率必须改

每小时一次对「告警」来说太慢。需要补：

| 触发 | 时机 |
|---|---|
| 定时 | 5–15 分钟一次（可配；现在固定 60 分钟） |
| 开机 / 重启 | `BootReceiver` 已存在，加一次上报 |
| 拨出/接入电话 | `CallTriggerReceiver` 已有入口 |
| 低电切换 | 电量跌破 20% / 开始充电 |
| 锁任务被关 | `lockTask` 由 true → false（说明有人退出了守护） |
| 定位开关变化 | `locateOn` 变化 |
| 手动 | 设置页「立即上报」按钮（已有） |

## 五、中继服务设计

### 5.1 接口

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | `/api/report` | 老人端上报（Body 即上面的 JSON） |
| GET | `/api/status?k=KEY` | 最新快照（家人端 App 用） |
| GET | `/api/track?since=` | 轨迹（家人端 App 用） |
| GET | `/api/check?k=KEY` | 连通性自检（替代 `check-remote.ps1` 的 DNS/端口两段） |
| GET | `/wx` | 公众号服务器配置验签（返回 echostr） |
| POST | `/wx` | 收用户消息，5 秒内回 XML |
| GET | `/m/<token>` | H5 地图页（微信里点链接打开） |
| POST | `/api/push/test` | 测试推送 |

### 5.2 表结构（SQLite）

```sql
device ( id TEXT PK, name TEXT, last_seen INTEGER, last_json TEXT )
track  ( device_id TEXT, t INTEGER, lat REAL, lon REAL, acc REAL, src TEXT )
event  ( device_id TEXT, t INTEGER, kind TEXT, detail TEXT, pushed INTEGER )
pushlog( t INTEGER, kind TEXT, device_id TEXT )   -- 用于去重
```

### 5.3 告警规则（复用 StatusReport 字段）

| kind | 条件 | 文案示例 |
|---|---|---|
| `offline` | `now - last_seen > 90 分钟` | 手机已 2 小时没上报，可能关机/断网 |
| `lowbat` | `battery < 20` 且 `charging = false` | 电量 15%，没在充电 |
| `muted` | `ringVolume = 0` | 手机被调成静音，来电不会响 |
| `nostorage` | `storageFreeMB < 500` | 存储只剩 380MB，可能收不到照片 |
| `lockoff` | `lockTask` true→false | 守护锁定被退出，桌面可能被换掉 |
| `locoff` | `locateOn` true→false | 定位服务被关了 |
| `recover` | 上一状态异常、本状态正常 | 电量已恢复 45%，已插上充电 |

**去重**：同 kind 同设备 30 分钟内只推一次；状态恢复时推一条 `recover`。避免老人手机整天低电就整天刷屏。

**合并**：一次上报触发多条规则时，合并成一条消息发（WxPusher 有 QPS 限制，也避免家人在微信里被连续弹窗）。

### 5.4 指令设计

家人真正会用的就几个，数字键最快（不用打字）：

| 输入 | 回复 |
|---|---|
| `1` / `位置` | 地址 + 「3 分钟前更新」+ H5 地图链接 |
| `2` / `电量` | 电量 + 是否充电 + 是否静音 |
| `3` / `在干嘛` | 屏幕是否亮 + 前台应用 + 今日使用时长 |
| `4` / `今天` | 今日使用排行（前 5） |
| `5` / `体检` | 全部字段 |
| `0` / `帮助` | 指令列表 |

**为什么 5 秒够**：查询读的是本地 SQLite 最新快照，毫秒级。绝对不能在回调里现场发起 GPS 定位或逆地理编码（会超时）。地图用链接而不是图片，也是这个原因（图片要先上传素材再发，容易超 5 秒）。

**鉴权**：`FromUserName`（openid）白名单。非白名单用户一律回「未授权」，不泄露任何数据。

## 六、成本

| 项 | 方案 | 费用 |
|---|---|---|
| 中继硬件 | 现有 OpenWrt 路由器 / NAS | 0 |
| 中继程序 | Go 单文件二进制（几 MB）或 Python3 标准库 | 0 |
| 主动推送 | WxPusher | 0 |
| 指令通道 | 个人订阅号（免费注册） | 0 |
| 公网入口（公众号需要） | Cloudflare Tunnel（本地 8899 → 公网 443） | 0 |
| 域名 | us.kg 免费 / 自购 | 0～50/年 |
| 可选：认证服务号 | 一步到位做模板消息 | 300/年 + 企业主体 |

**总计：0 元起步**，唯一隐性成本是需要一个域名（Cloudflare Tunnel 要求域名托管在 CF，dynv6 的免费域名不能托管）。

## 七、风险与待验证

| # | 风险 | 影响 | 应对 |
|---|---|---|---|
| 1 | 公众号服务器配置只支持 80/443，家庭宽带普遍封 80 | 配不上 | Cloudflare Tunnel 出 443；或用一台小 VPS 反代 |
| 2 | 微信是否接受非主流 TLD（us.kg 等） | 配置被拒 | 待实测；备选方案是买 .com/.cn |
| 3 | 5 秒被动回复超时 | 用户收不到回复 | 只读缓存；禁止在回调里做网络请求；超时返回空串避免重试 |
| 4 | WxPusher 第三方停服 | 推送中断 | 通道抽象成 notifier 接口，可切 PushPlus / Server酱 / 企微 |
| 5 | 家人把公众号消息设为免打扰 | 收不到告警 | 教程写清楚；关键告警用「服务通知」式账号；或改用企微应用消息 |
| 6 | 位置数据经过第三方 | 隐私 | WxPusher 只传文本摘要，原始坐标只存在自己中继 |
| 7 | 中继单点故障（路由器挂了） | 全断 | 家人端 App 可保留直连作为备份通道 |
| 8 | 老人端上报被系统杀 | 数据断流 | 上报走已有前台服务/JobScheduler；断网时本地排队，恢复后补报 |

## 八、落地分期

### 阶段 0（半天）· 零服务器验证价值

老人端加一个 `WxPusherNotifier`，把「低电 / 静音 / 失联」直接 POST 到 WxPusher API。

- 不改架构、不要域名、不要中继
- 只能单向推，没有指令
- 目的：**先确认家人是否真的会因为这条消息行动**。如果不看，后面做什么都白搭

### 阶段 1（2–3 天）· 中继 + 推送

- 路由/NAS 起服务，SQLite 落库
- `/api/report` 收上报，规则判定，WxPusher 推送
- 上报频率改可配（默认 10 分钟）+ 事件触发
- 简易 Web 看板（复用 `tools/family-locator.html`）
- 此时 DDNS 可退役

### 阶段 2（2–3 天）· 指令查询

- 注册订阅号，配服务器 URL（Cloudflare Tunnel）
- `/wx` 回调 + openid 白名单 + 指令路由
- H5 地图页 `/m/<token>`

### 阶段 3 · 收尾

- 历史轨迹页（7 天/30 天）
- 每日早上 8 点一份「昨日小结」推送
- 家人端 App 定位改为「深度查看工具」，不再要求手填地址密钥
- 可选：接 AI 把原始 JSON 转成一句人话（"昨天看了 3 小时短视频，晚上 11 点还在用"）

## 九、和现有功能的关系

| 现有功能 | 中继后的处置 |
|---|---|
| `LocateServer`（老人机当服务器） | 保留作为**离线兜底**，不再是主链路 |
| `DdnsUpdater` / `DdnsService` | 可退役（或保留给直连兜底用） |
| 家人端 App | 保留，定位从「直连老人机」改为「连中继」；不必再手填域名端口 |
| `ReportUploader` | 升级为「主上报通道」，频率可配 + 事件触发 |
| `check-remote.ps1` | 简化（三段探测 → 一段 `GET /api/check`） |
| `SmsCommandReceiver` | 保留，作为**完全没有网络时的最后通道**（短信不需要数据网） |

**重要**：短信通道不要撤。微信依赖数据网，老人机断流量时短信仍能到。微信是「日常」，短信是「兜底」。
