# 远程运维与无线调试 · 调研与方案（2026-10-25）

> 你问的是：DDNS 缝进来之后能不能做远程无线调试？已 ROOT 的手机能不能开外网调试？
> 再往下是：能不能让 AI 远程修问题、并把老人的使用习惯作为修复依据。

先说三条结论，后面是论证和可落地的路线。

1. **非 root 的 Android 10，远程 ADB 无法持久化**——重启就没了，这是系统机制，不是技术难题。
2. **DDNS 解决的只是"地址会变"，不解决"ADB 没开"**。两个问题不能混为一谈。
3. **"远程修正问题"其实不需要 ADB**。我们已经具备 Device Owner + 常驻服务 + 短信通道，做一个「运维指令集」比开 ADB 更安全、更稳、更能覆盖真实场景。**建议主攻这条，ADB 只做备用。**

---

## 一、远程 ADB 的五条路，逐条评估

| 方案 | 适用 | 重启后是否还在 | 需要 root | 风险 | 结论 |
|---|---|---|---|---|---|
| A. `adb tcpip 5555` + 端口映射 | Android 10（本机） | ❌ 不在 | 否（但每次要插线开） | 高（5555 无鉴权，等于后门） | 只做内网临时用 |
| B. 无线调试（Android 11+）+ `adb pair` | 新机 | ❌ 多数机型关 | 否 | 中 | 本机是 Android 10，用不上 |
| C. Tailscale / ZeroTier + `adb connect` | 任意 | 网络在，端口不在 | 否 | 低（自带鉴权、不开端口） | 跨网首选，但仍要解决"端口没开" |
| D. Magisk 模块固化 5555（`service.d` 脚本） | 已 root | ✅ 在 | 是 | 高（等于永久后门） | **已 root 的机器唯一能做到"开机即在"的方案** |
| E. Shizuku | 无需 root | ❌ 需重新激活 | 否 | 中 | 已放弃（首次仍需电脑） |

### 关键细节

**A. `adb tcpip 5555`**
- 每次重启后 adbd 回到 USB 模式，必须再插线执行一次。
- 想要"开机自动开"，只能改 `persist.adb.tcp.port`（需要 root）或改 ROM。
- 5555 端口**没有任何认证**，同网段任何人 `adb connect` 上就能装木马、读短信、定位、截屏。所以只能内网用。

**C. Tailscale 的组合价值**
- 它给手机一个固定的内网地址（100.x.x.x），并且自带加密与 ACL，**不用做端口映射、不用 DDNS、不怕公网扫描**。
- 但 adb 端口仍需开启：非 root 需要每次插线，root 可以用 D 方案固化。所以 **C + D 才是"随时能连"的完整答案**。
- 手机上 Tailscale 是 VPN 常驻，耗电比零信任方案高一些，但对"只在需要时打开"的场景完全够用（家人打电话说有问题，让老人点一下 Tailscale 图标）。

**D. Magisk 固化（已 root）**
标准做法，新建 `/data/adb/service.d/adb_tcpip.sh`：

```sh
#!/system/bin/sh
setprop service.adb.tcp.port 5555
stop adbd
start adbd
```

重启后 adbd 直接监听 5555。**这就是你说的"应用管家"能固化 5555 的真正原因——它要么拿了 root，要么是系统签名。**

**DDNS 的位置**
- DDNS 只解决"公网 IP/前缀会变"。手机用移动数据时 IPv6 前缀通常稳定，但**地址本身会用隐私扩展轮换**；家宽重播号前缀会变。
- 真正的坑不是地址，而是：**ADB 端口没开 + 运营商对入站连接的限制 + 公网暴露的安全风险**。
- 所以：**DDNS 有价值，但只在"你用 IPv6 直连且手机端已固化 5555"时才成立**。这个组合风险最高，我不建议对父母机使用。

### 我的建议顺序

```
家人说"出问题了"
  ├─ 90% 场景：用「运维指令集」远程处理（不用 ADB）
  ├─ 8% 场景：老人在家 → 同一 WiFi，adb connect 192.168.x.x:5555
  └─ 2% 场景：老人在外 → Tailscale 内网连（手机点开 Tailscale）
```

## 二、真正该做的事：运维指令集（不用 ADB 也能远程修）

我们有 Device Owner，能做到的运维动作比想象的多，而且**不需要开任何危险端口**：

| 指令 | 实现 | 用途 |
|---|---|---|
| `diag` | 返回自检 9 项 + 电量 + 联网状态 + 最近崩溃 | 一眼看出哪里坏了 |
| `usage` | 返回近 7 天使用统计（Top 应用、启动次数、使用时长） | 判断"老人其实天天在用抖音，你却给移除了" |
| `cfg get/set` | 读写配置快照（卡片、白名单、锁定、报时…） | 远程改配置，不用教家人在设置里点 |
| `fix <项>` | 重新下发 DO 限制 / 重开无障碍 / 重设电池白名单 | 一键复原"被系统重置"的项 |
| `restart` | 重启本应用（必要时重启桌面进程） | 卡住了拉一把 |
| `log` | 导出最近 N 条本地日志 + 崩溃栈 | 远程定位问题 |
| `screenshot` | 截屏（DO 可禁用截屏，但我们自己可调用） | 看老人卡在哪个界面 |
| `install <url>` | 从指定地址下载 APK 并静默安装（DO 能力） | 修 bug / 补装应用 |

**下发通道三选一**（都不用自建服务器）：

1. **短信指令**：家人发 `#diag` / `#fix a11y`，老人机解析后回短信（已有的 `SmsCommandReceiver` 扩展即可）。
2. **定位服务端口**：把 `/loc` 那套 HTTP 扩展成 `/cmd?key=xxx&op=diag`，家人用网页点按钮。
3. **传包服务的上传通道**：家人上传一个 `command.json`，App 读取后执行。

安全边界：指令必须验密钥/白名单号码；`install` 只接受 https 且校验包名与签名。

> 这套东西做完，"远程修问题"的 90% 场景就闭环了，而且**没有 5555 被扫的风险**。

## 三、AI 远程修复怎么做（设计草案）

```
① 采集        老人机本地生成 diagnostic.json
               （自检结果 + 配置快照 + 7 天使用统计 + 最近 3 条崩溃）
② 上传/回传    家人端拉取（定位服务端口）或短信回传摘要
③ 诊断        家人把 json 丢给 AI（或 App 内置一次调用）
               → AI 输出"疑似原因 + 建议指令列表"
④ 执行        家人点一下，指令通过短信/HTTP 下发到老人机
⑤ 验证        老人机执行后重新跑一遍自检，把结果回传
```

**为什么"使用习惯"很关键**：很多"坏了"其实是配置不合理。

- 老人每天用抖音 40 分钟，但家人把抖音从桌面移除了 → 老人开始乱点找应用
- 老人常用微信，但微信被误加进了"周期清理"名单 → 一天被清 8 次，卡顿
- 老人 22:00–06:00 几乎不用手机 → 可以在这个时段把清理/播报降频，省电

实现成本很低：`UsageStatsManager` 聚合 `queryUsageStats(INTERVAL_DAILY, now-7d, now)`，按包名汇总 `totalTimeInForeground` 与启动次数，写进 `diagnostic.json`。加一个每周一次的快照即可。

**建议先做这个（半天工作量）**，它是后面 AI 诊断的原料，也是"看老人用得顺不顺"的唯一客观依据。

## 四、如果你确实要开远程 ADB：可用步骤

### 内网（推荐，零风险）

```powershell
# 每次重启后需要执行一次（手机需插线）
powershell -ExecutionPolicy Bypass -File tools\provision.ps1 -Wifi
# 然后同一 WiFi 的电脑上
adb connect 192.168.x.x:5555
```

### 跨网（Tailscale）

1. 老人机和你的电脑都装 Tailscale，登录同一账号
2. 老人机上按"内网"方式开一次 5555（或在已 root 的机器上用 Magisk 固化）
3. 电脑上 `adb connect 100.x.x.x:5555`

优点：不开端口、不暴露公网、自带鉴权。缺点：Tailscale 要常驻（可以只在排障时打开）。

### 公网 IPv6 + DDNS（不推荐对父母机使用）

```bash
adb connect [2408:xxxx:...:xxxx]:5555
```
- adb 28+ 支持方括号形式的 IPv6 地址
- 前置条件：手机有公网 IPv6、运营商允许入站、端口已开、地址已绑定 DDNS
- 风险：**5555 无认证，扫描器 5 分钟就能找到。等于把手机送人。**
- 若坚持，至少：只允许特定源 IP（路由器 ACL）、限时开启、用完立刻 `adb usb`

## 五、安全底线（这几条不要破）

1. 5555 永不映射到公网；要用就 Tailscale。
2. 运维指令必须验密钥/白名单号码，且每条都可审计（本地留一条日志）。
3. `install` 只接受 https，校验包名，校验签名（防止被换包）。
4. 远程截屏、读短信这类能力，默认关闭，家人手动开，用完自动关。
5. 所有"远程能力"的开关都放在设置页，且显示"最近一次被使用的时间"。

## 六、落地建议（按顺序）

| 顺序 | 事项 | 收益 |
|---|---|---|
| 1 | 使用统计快照（7 天 Top 应用 + 时长） | 一切诊断的原料，半天 |
| 2 | `diag` / `fix` / `restart` 三条运维指令（先走定位服务端口） | 覆盖 80% 远程排障 |
| 3 | 家人端网页加"诊断"页（展示 json + 一键执行指令） | 不用装 App |
| 4 | `-Wifi` + Tailscale 文档化（已提供 `-Wifi`） | 剩余 20% 场景 |
| 5 | root 机固化 5555（可选，只给你自己的测试机） | 实验性质 |
