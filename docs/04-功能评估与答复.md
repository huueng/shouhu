## 二、逐条评估

### 1. 看门狗：切走就自动跳回（aerial-guard 式）

**结论：可以做，但定位应该是「锁定任务失效时的兜底」，不是主方案。**
**优先级：中高（P1.5）**　**成本：小（约 100 行）**

- 能实现的原因：我们已经有无障碍服务（`ElderAccessibilityService`），`TYPE_WINDOW_STATE_CHANGED` 能拿到前台包名；Device Owner 身份允许后台拉起 Activity，不受 Android 10 后台启动限制。
- 逻辑：前台包名 ∈ {系统桌面, 设置, 任务管理器, 未知第三方} 且当前不在白名单 → 50ms 后 `startActivity(MainLauncher)`。
- 必须处理的三个坑：
  1. **抖动**：老人正在用的应用被误判 → 每 2 秒最多纠正一次，且白名单内的应用不拦。
  2. **循环**：如果我们的界面自己起不来，会疯狂拉起 → 连续纠正 5 次后放弃并记日志。
  3. **耗电与隐私**：无障碍常驻本身耗电，且能读屏幕内容（我们只取包名）。
- **不建议默认开启**：锁定任务已经能挡住 HOME/返回/多任务，看门狗只在"锁定任务被系统重置"或"没激活 DO"时才有价值。
- 我的建议：做成设置里的开关「离开桌面自动拉回（兜底）」，默认关，配一句说明"锁定任务正常时不需要开"。

### 2. 网页端口扫码传包（同 WiFi 快速传 APK）

**结论：技术上很轻，但建议做成独立小工具，不建议塞进老人守护。**
**优先级：中**　**成本：中（HTTP 服务 + 上传 + 二维码）**

- 实现路径：内嵌一个 200 行的 HTTP 服务（自己写 `ServerSocket` 即可，不必引依赖），局域网访问 `http://手机IP:8080`，页面支持上传/下载 APK；二维码可用 `zxing-core`（约 300KB）或直接大字显示 IP。
- **为什么不建议放进老人守护**：
  1. 老人机是长期联网设备，常驻开端口是攻击面；
  2. 我们的 App 有 Device Owner + 静默安装能力，一旦上传接口被利用，等于把手机交出去；
  3. 装机场景里电脑就在旁边，`adb install` 更快也更可控。
- **如果一定要内置**，必须三条同时满足：默认关闭 → 开启后 10 分钟自动关 → 上传需 6 位随机码（页面显示，且只监听局域网地址）。
- 更划算的替代：`tools/provision.ps1` 已经能装包，再加个 `-Push 文件` 直接 `adb install`，零成本。

### 3. 打电话 / 短信改内部 UI

**结论：强烈建议做，但要分两步；电话墙先做，短信只读后做。**
**优先级：高（P2 首位）**　**成本：中（电话墙 ~200 行；短信只读 ~300 行 + 新权限）**

- **电话墙（建议立刻做）**
  - 大卡片：头像 + 名字（读通讯录，`READ_CONTACTS` 已有），点一下直接 `ACTION_CALL`。
  - 顶部固定「家人」分组（从联系人卡片里取），下面才是全部联系人，避免老人翻找。
  - 通话结束自动回主界面：已有 `CallTriggerReceiver` 监听 `PHONE_STATE`，`IDLE` 时判断"刚才是我们发起的通话"→ 拉起主界面。**这个能力现在就有，加 20 行即可。**
- **短信只读（建议第二步）**
  - 需要新增 `READ_SMS` 权限（DO 可静默授予，非 DO 需手动）。
  - 页面只做"列表 + 详情"，不提供输入框、不提供回复，从根上避免误发。
  - **风险提醒**：这是把家人之间的私人短信展示在老人机桌面上，家里如果有第三人在场要谨慎；建议只显示"最近 5 条 + 只显示白名单联系人"。
  - 原生短信 App 仍可通过「桌面图标」添加，两条路并存。
- 我的建议顺序：电话墙（1 天）→ 通话结束回桌面（半天）→ 短信只读（1 天，含隐私开关）。

### 4. 禁止安装 / 卸载：手机内可控吗？

**结论：只有 Device Owner 能控，这是系统硬限制，手机内无解；已补引导。**
**已做**：DO 激活时可直接开关；未激活时复选框置灰 + 弹窗说明原因、前提（无账号无锁屏密码）、命令，并支持一键复制。
**额外做了**：`setUninstallBlocked` 让本应用自己也不能被卸载（防家人误删、防老人乱点）。

### 5. 内置 ADB 命令 → 手机完全掌控？

**结论：不可行（不是难，是权限模型不允许），但 90% 的需求 Device Owner 已经覆盖。**
**优先级：不做（用 DO + 可选 Shizuku 替代）**

- 为什么不行：shell 权限来自 adb 的 `shell` uid，App 无论怎么装都拿不到；`Runtime.exec("sh")` 跑的是**本应用 uid**，不是 shell uid。没有 root 就没有"任意命令"。
- Device Owner 已经能做的事（我们已用/可用）：
  - 静默授予运行时权限 `setPermissionGrantState`
  - 禁用/启用应用 `setApplicationHidden`
  - 静默安装/卸载 `PackageInstaller`（DO 可免确认）
  - 禁止安装/卸载、锁定任务、状态栏、锁屏密码策略、恢复出厂
  - 禁用相机、截屏、USB 调试等
- 拿不到的部分：真正需要 shell 的（改系统属性、`settings put` 少数键、停系统服务）——这些恰好也不是产品必需。
- 结论：**不用做"内置 ADB"，把 DO 的能力做全就行**。

### 6. Shizuku 激活

**结论：不建议做（对老人机是负收益）。**
- Shizuku 的本质仍是"用 adb（或无线调试）启动一个高权限服务"，首次依旧要电脑或无线调试配对，**并没有比 `provision.ps1` 更省事**。
- 代价：多装一个 App、多一个常驻服务、老人机内存更紧张、Shizuku 重启后需重新激活（部分机型）。
- 唯一适用场景：家人自己有折腾能力、且不想每次插线。可以作为文档里的"进阶玩法"提一句，不进主流程。

### 7. 固化无线 ADB（5555）+ 外网调试

**结论：App 做不到"固化"；PC 脚本可以做"临时开"，外网暴露强烈不建议。**
**优先级：低（只做 PC 侧开关）**

- `adb tcpip 5555` 重启即失效；要固化必须改 `persist.adb.tcp.port` 或 init 脚本 → 需要 root 或改 ROM。你说的"应用管家"能固化，基本可以断定它拿了 root 或系统签名。
- 我们可以做的：`provision.ps1 -Wifi` → 执行 `adb tcpip 5555` 并打印 `IP:5555`，家人用同一 WiFi 的电脑重连。**重启后需重新插线开一次。**
- **安全红线**：5555 暴露到公网 = 任何人 `adb connect` 后就能装木马、读短信、定位。除非你确认：
  1. 只在路由器上做特定源 IP 白名单；或
  2. 走 Tailscale/ZeroTier 内网，绝不直接端口映射。
  我可以在脚本里加这个开关，但会在执行时打印这段警告。

### 8. 首次提示设置报时 / 天气 + 天气地点

**结论：已做（见第一节）。**

## 三、咨询：定位怎么直连家人手机？要不要服务器？IPv6 行不行？

先说结论：**"不要服务器"已经做到了（短信），但"实时看位置/看轨迹"必然要有数据通道，通道可以是 IPv6 直连，也可以是穿透，代价各不相同。**

### 3.1 现有方案的能力边界

短信通道：家人发「位置」→ 老人机定位 → 回一条带高德链接的短信。
- 延迟：10–60 秒（受运营商短信延迟影响）
- 成本：约 0.05 元/条，"跟踪 10" 就是 0.5 元
- 优点：不依赖任何服务、老人机只要有信号就行、天然点对点、隐私最好
- 缺点：不能实时、不能看轨迹、双卡/短信中心异常时不可靠、运营商可能限流

**如果需求是"我知道他在哪、有没有事"——短信已经够了，不必上服务器。**

### 3.2 想实时，四条路

| 方案 | 需要什么 | 延迟 | 成本 | 对老人机的影响 |
|---|---|---|---|---|
| A. 局域网直连 | 老人机在家、家里有常开设备（NAS/树莓派/旧手机） | 秒级 | 0 | 小，仅在家上传 |
| B. IPv6 直连家人机 | 两端都有公网 IPv6 + 家人端放行端口 + DDNS | 秒级 | 0 | 中，要维持连接 |
| C. 穿透（Tailscale / ZeroTier / frp） | 老人机装客户端 或 一台 VPS | 秒级 | 0–20 元/月 | **大**，常驻 VPN 耗电、老人机内存吃不消 |
| D. 轻服务器（云函数 / 自建） | 一台小机器或云函数 | 秒级 | 0–10 元/月 | 小，普通 HTTPS 上报 |

### 3.3 IPv6 到底行不行

行，但有四个前提，缺一个就得回退：

1. **两端都要有公网 IPv6**。现在移动/电信/联通的手机流量基本都有 IPv6；家宽多数也已下发，但**路由器默认防火墙会拦入站**，需要手动放行端口（老人端是"主动外连"，不受此限——所以建议**家人端做服务端、老人端主动上报**）。
2. **地址会变**。手机 IPv6 用隐私地址（RFC 4941），会周期性更换；家宽重新拨号前缀也会变。所以必须配 **DDNS**（把变化的地址绑到一个固定域名）。
3. **双栈回退**。凡有一点走不通（比如家人手机在只给 IPv4 的网络里），就得有回退路径，否则你会收到"有时候能看到有时候看不到"的投诉。
4. **耗电**。要"实时"就得长连接或高频轮询，老人机电池经不起；建议改成"移动超过 300 米才上报一次"。

**结论：IPv6 能省掉服务器，但省不掉 DDNS + 端口 + 回退逻辑的复杂度。对个人自用可以玩，对给父母用的产品，短信 + 局域网兜底更稳。**

### 3.4 我的推荐落地顺序

1. **现在**：短信（已有）作为兜底，任何情况下都能用。
2. **下一步（性价比最高）**：加一个"到家报平安"——连上家里 WiFi 就发一条短信。**零成本、零服务器、家人感知最强。**
3. **家里有 NAS/树莓派/OpenList 的话**：老人机在家时把位置 POST 到家里的 `http://NAS:xxxx/loc`，家人通过你已有的远程访问（OpenList/飞牛/TVDesk）看轨迹。**零公网成本，还不用穿透。**
4. **真要公网实时**：优先 Tailscale（不暴露端口、自带穿透与鉴权），其次 IPv6 + DDNS，最后才是自己写服务器。
5. 不建议做的事：把 5555 或任何管理端口映射到公网。

### 3.5 一句话总结

> 短信解决"人在哪"，局域网解决"在家时"，IPv6/穿透解决"随时随地"。
> 三者不是替代关系，是分层兜底——先做前三步，第四步等你真的需要看轨迹再说。

## 补充（2026-10-26）：首次发短信要输 4 位验证码，是谁弹的？

**结论：手机的（EMUI / Android 的「受限权限」机制），不是本应用。**

判断依据：

1. 本应用源码里没有任何验证码 UI、没有输入框、没有校验逻辑——短信是
   `SmsManager.sendMultipartTextMessage()` 直接发的，中间没有界面。
2. `dumpsys package com.elder.launcher` 里可以看到：

   ```
   android.permission.SEND_SMS: restricted=true
   android.permission.SEND_SMS: granted=true, flags=[POLICY_FIXED|...|RESTRICTION_INSTALLER_EXEMPT]
   ```

   `SEND_SMS` 属于 Android 的 **restricted permission（受限权限）**，
   系统要求"安装方白名单"或**由用户亲自确认**，EMUI 把确认做成了 4 位验证码。
3. 时间线对得上：验证码只在这个应用**首次**发短信时出现一次，之后不再出现。

**要不要处理：**

- 一次性成本，验证过就好了，重装/清数据后会再来一次。
- 想彻底避开，只能把守护设为「默认短信应用」（要接管 SMS_DELIVER 等一整套组件），
  代价远大于收益，**不建议**。
- 部署时提前告知家人「第一次会自动发一条短信，可能要输 4 位验证码」即可。
