# 15 · 中继服务部署三档分析（OpenWrt / NAS / VPS）

> 调研日期：2026-10-26
> 用途：接收老人端上报 → 判定围栏 → 推送微信。**只做这一件事**，不做指令、不做 Web 后台（第一版）。

---

## 一、先把「公网 IP」讲清楚

你的疑问是「需要公网 IP」。拆开看，其实只有一个环节需要：

```
老人端（客户端） ──出站请求──→ 中继（服务端）
```

| 角色 | 需要公网 IP 吗 |
|---|---|
| 老人端 | **不需要**。它只往外发请求，在 NAT 后面完全没问题 |
| 中继 | **需要「能被访问到」**，但不等于需要公网 IPv4 |

关键区分：

| 场景 | 老人端在哪 | 中继要求 |
|---|---|---|
| 老人只在家 | 同一 WiFi / 局域网 | **不需要任何公网**，局域网直连 |
| 老人出门 | 4G / 5G | **需要公网可达** |

**电子围栏的核心场景就是「出门」，所以公网可达是硬前提，绕不过去。**

但「公网可达」有四种实现，成本差别很大：

| 路径 | 前提 | 成本 | 国内实际可用性 |
|---|---|---|---|
| **IPv6 直连** | 家里宽带下发 IPv6 + 防火墙放行 + DDNS 更新 AAAA | 0 | 好（你已在用，`dynv6` 已跑通） |
| **VPS 中转** | 一台有公网 IPv4 的机器 | 100–300/年 | 最好，完全不用管 NAT |
| **Cloudflare Tunnel** | 域名托管在 CF | 0 | 一般（国内线路抖动，偶尔几秒超时） |
| **frp / rathole 反向隧道** | 仍需一台有公网的机器 | 同 VPS | 好 |
| NAT 打洞（STUN） | 双方 NAT 类型友好 | 0 | 不可靠，不适合守护类 |

**重要事实**：国内三大运营商的 4G/5G **基本都分配 IPv6**，所以老人端在移动数据下大概率能拿到 IPv6；家庭宽带的 IPv6 也是公网可路由的（只要路由器防火墙放行 inbound）。

→ **你现在这套 IPv6 + DDNS 的能力已经覆盖了最省钱的那条路**，不需要额外买公网 IP。你保留 DDNS 的判断是对的。

→ 唯一的不确定性是「某些 APN / 某些老路由器 / 企业 WiFi 没有 IPv6」。所以建议：**老人端支持配置 2 个上报地址，主失败切备**。这个改动很小，但把单点风险直接消掉一半。

## 二、三档总览

| 维度 | OpenWrt 路由器 | NAS | VPS |
|---|---|---|---|
| 典型算力 | MIPS 880MHz / ARMv7 双核，128–512MB 内存 | x86 或 ARMv8 四核，2–8GB | 1 核 1G |
| 可用存储 | **瓶颈**：flash 16–128MB，overlay 常只剩 2–10MB | TB 级 | 20–40GB |
| 常开 | 是（本来就在跑） | 多数是（做相册/下载） | 是 |
| 公网可达 | 需 IPv6 + 防火墙放行 | 需 IPv6 + 防火墙放行 | **自带 IPv4，零配置** |
| 部署方式 | 交叉编译 + scp / opkg | Docker 一键 | Docker / 二进制 |
| 可靠性 | 中（刷机、重启、掉电） | 高 | 高 |
| 边际电费 | **0**（本来就开着） | 0（本来就开着） | 不含电费 |
| 年费 | 0 | 0 | 100–300 |
| 数据落地 | 在家 | 在家 | 上云 |
| 长期轨迹 | 存不下 | **随便存** | 存得下但不划算 |

## 三、OpenWrt 路由器

### 3.1 能跑什么

| 项 | 实际情况 |
|---|---|
| Go 静态二进制 | 可行。交叉编译 `GOOS=linux GOARCH=mipsle GOMIPS=softfloat`（老 MT7620/7621）、`arm`（armv7）、`arm64`。**体积约 8–15MB**（含 net/http、TLS、JSON） |
| 内存占用 | RSS 约 **15–30MB**（HTTP 服务 + 内存索引）。这是估算，建议实测 |
| Python3 | 可行但吃内存（30–60MB），且 opkg 装依赖容易爆 flash，不推荐 |
| SQLite | 需要 CGO，交叉编译麻烦。**改用纯 Go 的 bbolt**（单文件 KV，几 MB）或「每日一个 JSON 文件 + 内存索引」 |
| Node.js | 不推荐，体积和内存都超标 |

### 3.2 真正的瓶颈是存储，不是算力

多数家用路由器：

- flash 16MB 的（如老款 MT7620），overlay 装完基本没空间 → **二进制放不进去**
- flash 128MB 的（如 MT7621 + NAND），能放，但日志写 flash 会加速磨损

**解法**：挂一个 U 盘（ext4），二进制和数据都放 `/mnt/usb/elderguard/`。这几乎是必须的。

### 3.3 什么时候适合

- ✅ 已经有 OP 且**挂了 U 盘**
- ✅ 只要「接收 + 判定 + 转发」，不存长期轨迹
- ✅ 不想为这事多开一台设备
- ✅ 内存 ≥ 128MB

### 3.4 什么时候不适合

- ❌ flash 16MB 且没有 U 盘（放不下）
- ❌ 内存 < 64MB
- ❌ 路由器经常手动重启、刷固件（数据会丢）
- ❌ 想存 3 个月以上轨迹

### 3.5 部署要点

```
/mnt/usb/elderguard/
├── relay            # Go 二进制（chmod +x）
├── data.db          # bbolt
└── relay.log        # 限制 10MB 轮转
```

- 用 `procd` 写 `/etc/init.d/elderguard` 做守护（crash 自动拉起）
- 日志写 U 盘，不要写 `/tmp`（重启丢）也不要写 flash
- 路由器重启后要能自启（`enable`）

## 四、NAS

### 4.1 优势

- Docker 一键部署，镜像约 20MB
- 存储充裕：**可以存全部轨迹、历史围栏事件、每日快照**，不担心清理
- 可以顺便跑 Web 看板、Caddy（TLS）、备份
- 通常 24h 开着

### 4.2 劣势与坑

| 坑 | 对策 |
|---|---|
| NAS 会休眠硬盘，Docker 容器可能被挂起 | 关掉硬盘休眠，或容器内定时写心跳保活 |
| 多数 NAS 的公网仍需 IPv6 或隧道 | 同 OpenWrt，靠 IPv6 + DDNS；或前置 VPS |
| NAS 升级/重启 → 中继中断 | `restart: unless-stopped` + 老人端本地排队补报 |
| 群晖/威联通 Docker 的网络模式差异 | 用 host 网络模式最省事 |

### 4.3 部署要点

`docker-compose.yml` 大致长这样（示意）：

```yaml
services:
  elderguard:
    image: elderguard/relay:0.1
    restart: unless-stopped
    network_mode: host
    volumes:
      - ./data:/data
    environment:
      - PUSH_TOKEN=xxx
      - TZ=Asia/Shanghai
```

数据卷挂在 NAS 的存储池上，备份跟着 NAS 的备份策略走。

### 4.4 什么时候适合

- ✅ **有 NAS 且支持 Docker**（最优解）
- ✅ 想存长期轨迹
- ✅ 愿意让 NAS 24h 不休眠

## 五、VPS

### 5.1 唯一的核心优势

**自带公网 IPv4。** NAT、IPv6、DDNS、防火墙放行、运营商封端口——全部不用管。

这对「老人出门也要能上报」来说，是把不确定性一次性买断。

### 5.2 成本与坑

| 项 | 说明 |
|---|---|
| 配置 | 1 核 1G 足够（常驻内存 < 50MB） |
| 年费 | 国内轻量约 100–200/年；香港/海外约 150–300/年 |
| 国内节点 80/443 | 需 ICP 备案。**用非标端口 + IP 直连可以规避**（老人端本来就是填 URL） |
| 香港/海外节点 | 无需备案，延迟 30–80ms（对上报完全无感） |
| 数据隐私 | 位置数据出家门，建议库里加密存坐标 |

### 5.3 一个附加价值：能感知「家里断网」

中继在云端时，如果老人端连续 N 小时没上报，中继可以确定是**老人端侧的问题**（关机/断网/没电），从而推「失联告警」。如果中继在家里，家里宽带断了它自己也挂了，没人报警。

**这是 VPS 方案独有的可靠性优势。**

## 六、混合方案（按性价比排序）

### 方案 A：NAS 主 + IPv6 直连（成本 0，推荐先做）

```
老人端 ──IPv6──→ NAS（判定 + 推送 + 存全量）
```
- 用现成的 `DdnsUpdater` 更新 AAAA
- 老人端配 2 个地址：主 = NAS 的 IPv6，备 = （后续加）
- 成本 0，数据不出门

**唯一风险**：老人端没有 IPv6 时上报失败。靠「老人端本地排队 + 有网再补报」兜底。

### 方案 B：NAS 主 + VPS 备（成本约 100/年，最稳）

```
老人端 ──主：NAS 的 IPv6
        └─备：VPS 的公网 IPv4（失败才用）
VPS 只做转发，把数据回传给 NAS（或自己存一份）
```
- 老人端只需支持「多个上报地址，按顺序 fallback」
- IPv6 不通时自动走 VPS
- 成本低，可靠性接近 100%

### 方案 C：纯 VPS（成本 100–300/年，最省心）

- 不用管 IPv6、不用管 DDNS、不用管防火墙
- 顺带获得「家里断网也能告警」的能力
- 缺点：位置数据在云上

### 方案 D：OpenWrt 单跑（成本 0，最不推荐）

只在「不想开 NAS、路由器有 U 盘」时考虑。稳定性和存储都吃亏。

## 七、给你的选型建议

你手上有 **OpenWrt + NAS**，所以：

| 优先级 | 方案 | 理由 |
|---|---|---|
| **1** | **NAS（Docker）+ IPv6 直连** | 成本 0、存储够、部署最简单、数据在家 |
| **2** | NAS + 一台最便宜的 VPS 做 fallback | 补掉 IPv6 的不确定性，100/年买确定性 |
| **3** | 纯 VPS | 如果 NAS 不常开、或不想折腾 IPv6 防火墙 |
| **4** | OpenWrt | 只在没有 U 盘以外的特殊理由时用 |

**OpenWrt 的性能担忧是成立的**，但真正卡住的通常不是 CPU，而是 **flash 空间**。如果那台 OP 路由器没有 U 盘，基本不用考虑它。

## 八、需要你确认的信息

| # | 需要知道 | 为什么 |
|---|---|---|
| 1 | NAS 型号 + 是否支持 Docker | 决定能否用方案 A |
| 2 | NAS 是否 24h 常开、是否开硬盘休眠 | 决定可靠性 |
| 3 | 家里 IPv6 前缀是否稳定（多久变一次） | 决定 DDNS 更新频率 |
| 4 | OpenWrt 型号 / 内存 / flash / 是否有 U 盘 | 决定它能不能当备选 |
| 5 | 老人端出门时，是否稳定能拿到 IPv6 | 决定要不要 VPS |
| 6 | 是否愿意为这件事花 100/年 | 决定方案 B/C |

---

## 九、结论

- **「需要公网 IP」这个担忧减半**：中继需要的是「可被访问」，你现在这套 IPv6 + DDNS 已经满足，不必额外买公网 IP。
- **NAS 是最合适的落点**，OpenWrt 受限于 flash 空间，VPS 是买确定性。
- **强烈建议老人端支持多上报地址 fallback**——这是把三档方案串起来的关键，改动很小，收益最大。
